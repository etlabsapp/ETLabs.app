```
# uptime

# nproc
8
# vmstat 1 3
r  b   swpd    free   buff  cache  si  so  bi  bo   in   cs  us sy id wa st
16 0  10240 7420112  2048 154220   0   0   0   0 8120 2770  99  1  0  0  0

              total   used   free  shared  buff/cache  available

```
What will help the jobs finish faster?

- Add more disks. :: vmstat shows bi, bo and wa all at 0. The jobs are not waiting on disk.
* Give the system more CPU resources. :: A load average near 16 on 8 CPUs means jobs are queued for a CPU. vmstat shows 16 runnable tasks (r), 99% user time and 0% idle, so the CPUs are maxed out. More CPU lets more jobs run at once.
- Add more free memory. :: free shows 6.9Gi available, so memory is not the bottleneck.

- tar -c -f /srv/backup/site.cpio /var/www/site/ :: -c creates an archive. This would overwrite the backup with a new archive of the web folder, destroying it.
* pushd /var/www/site/ && cpio -idv < /srv/backup/site.cpio && popd :: pushd moves into the target folder and remembers where you were. cpio -i extracts the archive from standard input, -d creates folders as needed and -v lists each file. popd returns you to where you started.

@ 3
After maintenance, an admin cannot mount a logical volume:
```
# mount /dev/vgapp/logs /srv/logs
mount: /srv/logs: special device /dev/vgapp/logs does not exist.
# lvs
  LV   VG    Attr       LSize
  logs vgapp -wi------- 2.00g
# vgs
  VG    #PV #LV #SN Attr   VSize  VFree
  vgapp   1   1   0 wz--n- 5.00g  3.00g
```
Which command is the usual fix?
- lvscan --all :: lvscan only lists logical volumes and whether they are active. It does not change anything.
- vgimport vgapp :: vgimport is only used after vgexport, when moving disks to another system. vgs shows the group is present and not exported.
* vgchange -ay vgapp :: The volume group and LV still exist, but the LV is not active (no "a" in its Attr), so no device file was created. vgchange -ay activates every LV in the group and creates the device files, so the mount works. (lvchange -ay on just that LV would also work, but vgchange -ay is the usual step after maintenance.)
- mkfs.xfs /dev/vgapp/logs :: The device does not exist yet, and making a new filesystem would wipe the data anyway.

@ 6
Users cannot reach an HTTPS site. The admin sees:
```
# ufw status
Status: active
To                Action   From
--                ------   ----
443/tcp           DENY     Anywhere
443/tcp (v6)      DENY     Anywhere (v6)
# ss -lnt | grep 443
LISTEN 0  511  *:443  *:*
```
What is the best fix?
* ufw delete deny 443/tcp :: The web server is listening on 443, but ufw has a DENY rule for 443/tcp. Removing just that rule lets HTTPS in while every other firewall rule stays in place.
- ufw allow 511/tcp :: 511 in the ss output is the listen backlog, the size of the waiting-connection queue, not a port.
- ufw disable :: This would let HTTPS through, but it turns off all firewall protection when only one rule is wrong.
- ufw allow 80/tcp :: Port 80 is plain HTTP. HTTPS on 443 would still be blocked.

@ 23
A PostgreSQL server keeps throwing errors. The admin sees that swap is almost used up:
```
              total     used     free
Mem:        2047600   301220  1746380
Swap:       2097148  2081004    16144
SwapTotal:  2097148 kB
SwapFree:     16144 kB
```
Which two changes help keep the database running even if the system runs out of swap? (Choose two.)
* Run sysctl -w vm.overcommit_memory=2 :: Mode 2 is strict accounting: the kernel refuses memory requests beyond its commit limit up front, instead of promising memory it cannot deliver and later calling the OOM killer on a big process like the database.
- Use disk quotas on the swap space to limit PostgreSQL. :: Disk quotas limit file storage per user. They do not apply to swap.
- Run mount -a to reload /etc/fstab. :: mount -a mounts filesystems listed in fstab. It does not add memory or change how memory is handed out.
- Run dd if=/dev/zero of=/swapfile bs=1M count=64 :: This only creates a blank 64 MB file. Without mkswap and swapon it is never used as swap.
* Run sysctl -w vm.overcommit_ratio=100 :: In strict mode the commit limit is swap plus this percentage of RAM. Raising it from the default 50 to 100 lets all of RAM count, so the database can still get memory when swap is gone.
- Run mkswap /dev/sdz2; swapon /dev/sdz2 :: This adds swap, but only if that partition exists and is free. It does not change how the kernel handles running out.
